# 2 Detailed description of unit test strategy

The unit tests were designed using equivalence class testing, a black-box testing technique that divides the input domain into classes of data from which test cases are derived.

For each method under test, the input space was systematically analyzed and partitioned into equivalence classes. An equivalence class represents a set of valid or invalid inputs that are expected to be treated similarly by the system. If one test case in an equivalence class detects a defect, all other test cases in that class would likely detect the same defect; conversely, if one test case does not detect a defect, none of the others in that class would either.

For example, the combine method in the Range class was partitioned along the following dimensions:
- Null Status: Whether each range parameter is null or non-null
- Range Relationship: Whether the ranges are intersecting, touching, non-intersecting, or one contains the other
- Order: Whether the ranges are provided in numerical order or reverse order

These partitions resulted in 12 distinct equivalence classes, producing the following test cases:
- combine_BothRangesNull
- combine_Range1Null
- combine_Range2Null
- combine_SameRange
- combine_TouchingRangesInOrder
- combine_TouchingRangesNotInOrder
- combine_IntersectingRangesInOrder
- combine_IntersectingRangesNotInOrder
- combine_NonIntersectingRangesInOrder
- combine_NonIntersectingRangesNotInOrder
- combine_RangeInsideRangeInOrder
- combine_RangeInsideRangeNotInOrder

This systematic approach ensures comprehensive coverage of the method's behavior across all meaningful input variations while maintaining an efficient and manageable test suite.

# 5 Difficulties encountered, challenges overcome, and lessons learned

Throughout the development and execution of our black-box test suite for JFreeChart v1.0, we encountered several conceptual, technical, and collaborative challenges that influenced both efficiency and accuracy.

One of the primary difficulties was defining correct input partitions strictly from the documentation rather than from the implementation. Because the assignment required black-box testing, we had to rely entirely on the specification to determine expected behavior. In some cases, documentation lacked detailed clarification regarding edge cases (e.g., null handling or boundary conditions), making it challenging to determine the correct expected outcome. When a test failed, it was not immediately clear whether the failure was due to an implementation defect (which was intentionally introduced in this version of the system) or an incorrectly designed test. This required careful re-evaluation of test logic to ensure assertions were specification-driven rather than based on observed behavior.

Black-box testing itself proved time-consuming. Without direct visibility into the underlying source code, additional effort was required to ensure that failures reflected actual system defects and not errors in mocking configuration, incorrect assumptions, or faulty assertions. Because the provided library consisted of compiled .class files rather than source .java files, we initially could not inspect the internal logic. This required installing and configuring a decompiler plugin in Eclipse to interpret the compiled classes, which added an additional tooling setup step before meaningful debugging could occur.
We also faced IDE configuration challenges. The project initially failed to run correctly due to Java version mismatches within Eclipse. We had to manually configure the correct JDK version and adjust the project build path to ensure compatibility with JFreeChart and our testing libraries (JUnit and Mockito). This setup issue delayed early progress and required troubleshooting before tests could be executed successfully.

Collaboration via GitHub introduced additional complexity. Since multiple team members were working on different test cases simultaneously, maintaining synchronization across branches was essential. We experienced issues with outdated branches, merge conflicts in shared test files, and pull request inconsistencies. To ensure that our tests remained up to date, we had to regularly pull from the main branch, resolve conflicts manually, and rerun the entire test suite locally before submitting pull requests. Ensuring that new tests did not break existing ones required disciplined version control practices and careful review of changes.
Finally, because the provided system contains intentional defects, several correctly written tests failed. Maintaining specification-based assertions despite failing results required discipline. It was important not to modify expected outputs to match buggy behavior, but instead to document failures accurately and trace them to likely implementation defects.

Overall, the process highlighted the challenges inherent in specification-driven testing, collaborative version control, environment configuration, and defect identification without direct source access. Despite these obstacles, the experience strengthened our understanding of rigorous black-box testing and structured test design.
